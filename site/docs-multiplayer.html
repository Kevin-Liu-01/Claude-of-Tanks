Configure a room, then enter battle

A T-90A is knocked out at the end of a Steinburg street at night

Create or join a room from the separate Multiplayer control. The current v2 connection uses WebRTC between browsers; the host browser runs the authoritative match, while the room service handles membership and connection signaling.

3 min

Create, join and configure

Set a callsign, choose the room format and create a room, or enter an invite code to join. Share the invite link with your friends. Configure teams, vehicles, camouflage, battlefield and mode rules before readying up. Opening Multiplayer does not start a battle. Room identities belong to players; several players may select the same tank.

Private rooms use the configured room service; LAN uses the local helper where available. A service or connection failure stays on the setup screen with a clear recovery action. Recheck the code for an invalid invitation, retry an interrupted connection, or return to the garage. The current entry does not require a version flag or a legacy signaling-address field.

The host runs the match

The room Worker coordinates discovery and signaling. It does not run the sixty-step battle simulation. The host browser runs the match authority and exchanges WebRTC data with peers. Guests send inputs; the host resolves movement, firing, reloads, collisions, damage, bots and results. This differs from the older dedicated-server architecture still documented for historical reference.

The local vehicle predicts movement and reconciles against acknowledged host state; remote vehicles interpolate snapshots. Nearby and recently engaged opponents refresh more often than distant visible actors. Combat events remain ordered independently of those interest tiers. Prediction improves responsiveness but cannot award a hit or change the authoritative result.

Visibility and trust

Guest snapshots contain only enemies the viewer is allowed to see. Filtering occurs before encoding, so hidden coordinates are not simply sent and concealed by the renderer. Team vision and spectator perspective also govern nameplates, minimaps and presentation.

A browser host is still a participating player’s machine and must hold the authoritative world. Peer hosting should not be described as having the same trust boundary as an independent dedicated server. The protocol checks input ordering and message shape; it cannot turn an untrusted host into trusted tournament infrastructure.

Leaving, reconnecting and host migration

Connection state is visible during room and match transitions. If the host leaves or loses its connection, the v2 session has a migration path that transfers the match to a remaining eligible peer using its retained migration state. Recovery depends on surviving peers and usable connectivity; closing every participant ends that possibility.

Backpressure and stalled channels are bounded rather than allowing unlimited queued snapshots. A delayed peer should receive fresh state when it recovers. Repeated failures should include the application version, room format, map, browser and which player was hosting in the report. Do not expose invite codes or private room links in public diagnostics.

What the tests cover

Current certification exercises browser-to-browser entry, input and snapshot exchange, visible combat, interruption, migration and large-team traffic. The 14 v 14 bandwidth work measures host uplink and snapshot timing as well as positional drift. These results describe the tested network conditions; real Wi-Fi, mobile radios, firewalls and suspended browser tabs can behave differently.

Run npm run test:net:v2:p2p for the three-browser peer-to-peer gate: a host and two peers move and fire, then migrate the host. The former ranked and dedicated-server stack has been removed; MULTIPLAYER-V2.md owns the current room and match contract.
