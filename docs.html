01 // System overview

A game engine organized around authority boundaries.

Claude of Tanks separates gameplay truth from browser presentation. Movement, aiming, ballistics, armor, damage, spotting, bots, and match results can run without the DOM or WebGL. Three.js consumes those results and constructs the visible world.

This division supports three execution arrangements without changing the rules: an in-page solo authority, a browser-hosted WebRTC authority for private and LAN rooms, and a renderer-free dedicated authority for ranked service play. The same simulation vocabulary is used in every arrangement; transport and presentation are adapters around it.

01

Deterministic authority

Simulation advances in fixed 1/60-second steps. Authoritative randomness is seeded or injected, never read from wall-clock time.

02

Explicit ownership

Each subsystem owns one policy boundary. Rendering cannot decide hits; clients cannot grant damage; hidden transforms never leave authority.

03

Measured delivery

Focused self-tests, browser probes, asset fingerprints, geometry gates, and public/private builds verify the behavior users receive.

Scope statementAll vehicle values and diagnostic overlays describe the game simulation. They are not real-world engineering, protection, or survivability assessments.

02 // Architecture

One direction for truth; several consumers.

The main data path is intentionally linear. Controls become bounded intent. Authority advances the match and emits durable state plus reliable one-shot events. Presentation samples that state, renders it, and reports input back through the same intent interface.

INPUTControl intent

Drive, aim point, fire edge, ammunition, equipment, and room actions.

AUTHORITYDeterministic match

Movement, combat, spotting, bots, world collision, timers, and result.

DELIVERYState + events

Direct calls, viewer-filtered snapshots, acknowledgements, and reliable events.

CLIENTPresentation

Three.js visuals, interpolation, HUD, audio, effects, killcam, and reports.

03 // Runtime lifecycle

Boot only what the current phase requires.

Startup prioritizes a responsive garage. Battlefield composition, multiplayer adapters, high-cost source geometry, and optional tools remain outside the critical path until a user action makes them necessary.

Document and renderer boot

The inline entry screen paints first. Vite prewarms the static game module graph in development; the renderer and device policy then establish a recoverable WebGL surface.

Garage composition

The selected specification is constructed with createTank(), placed on the garage stage, and paired with roster, map, equipment, and session controls.

World activation

Battle entry creates or restores the chosen map, prewarms required vehicle/material variants, builds the roster, and starts an authority arrangement.

Fixed simulation and sampled presentation

The accumulator advances bounded 60 Hz steps. Rendering remains variable-rate and samples the latest local or network state.

Result and reset

The authoritative result produces an after-action report. Returning to the garage clears match-specific state while retaining reusable immutable resources.

04 // Vehicle system

A specification, an authority state, and a visual rig.

A vehicle is not a single object. Its stable specification identifies balance and geometry. Its authority state records the current match. Its Three.js rig presents that state without becoming authoritative.

specificationimmutable contract

Dimensions, mass, engine output, speeds, traverse limits, weapon data, armor plates, internal volumes, crew, labels, and appearance metadata.

  • Registry: src/vehicles/specs.js
  • Stable key: vehicle spec ID
  • Display copy: canonical label record
authority statematch truth

Entity identity, position, yaw, speed, aim, ammunition, reload, hit points, modules, crew, visibility, destruction, and contribution.

  • Player ID and spec ID are independent
  • Duplicate vehicle selections are valid
  • One authority owns every mutation
visual rigpresentation

A procedural hierarchy of hull, turret, gun, recoil group, fittings, running gear, tracks, materials, anchors, and state-driven effects.

  • Tank forward is local +Z
  • Runtime units are metres and radians
  • Articulation mirrors authority state
asset recordgenerated proof

Hero, side, top, silhouettes, armor, module, hit-zone, and marking views are generated from live geometry and bound to metadata and geometry fingerprints.

  • Generated assets fail closed when stale
  • Public builds strip quarantined references
  • Geometry remains the source of truth

Construction pipeline

REGISTRYCanonical spec

Mobility, weapon, dimensions, armor volumes, family, and label.

FACTORYProcedural rig

Family builder, bucket merge, materials, fittings, running gear, and LOD.

CONSUMERSGame + tools

Garage, battle, gallery, Studio, icon generator, and geometry probes.

Open the Tank Gallery to inspect the current registry as live geometry. Armor, module, and crew layers are generated directly from the authored diagnostic volumes.

05 // Combat simulation

Physical intent, resolved once.

movement.jsmobility

Converts normalized controls, drivetrain parameters, terrain support, and collision context into authoritative position, heading, velocity, hull attitude, and track travel.

ballistics.jsprojectiles

Spawns shells from the resolved muzzle, advances travel and gravity, and finds the first eligible world or vehicle impact.

armor.jspenetration

Transforms the impact into plate space and evaluates slope, obliquity, normalization, ricochet, overmatch, spaced layers, ERA, and kinetic/chemical resistance.

damage.jsconsequence

Applies vehicle damage, module and crew effects, fire, repair state, destruction cause, and event data used by the HUD and killcam.

Aiming order

  1. Input identifies a finite world-space aim point.
  2. Authority converts it to bounded yaw, pitch, and distance intent.
  3. The turret and gun approach the permitted solution at spec-defined rates.
  4. The actual muzzle transform is resolved after articulation.
  5. Dispersion is applied and the shell begins physical travel.
  6. Impact is resolved once; presentation receives the result.
Killcam invariantThe X-ray killcam is a projection of the resolved shot. It does not repeat armor or damage calculations and cannot produce a second outcome.

06 // Multiplayer authority

The client requests actions; authority grants outcomes.

Private/LAN and ranked play share the same protocol and match runtime. Their transport and authority location differ. The browser-hosted arrangement uses WebRTC; dedicated play uses an ordered WebSocket service. Both validate intents and publish viewer-specific state.

Client-owned

Presentation and requested intent.

  • Normalized controls
  • Finite aim request
  • Local movement prediction
  • Snapshot interpolation
  • HUD, audio, effects, and reports
Trust boundary

Authority-owned

All value-granting decisions.

  • Movement acceptance
  • Reload and firing
  • Hits and damage
  • Spotting and hidden state
  • Destruction and match result

Delivery classes

ClassExamplesDelivery rule
Durable statePose, hit points, reload, modules, visibility, destructibles, result.Snapshot state; later values supersede earlier values.
Reliable eventsShot, impact, destruction, module alert, match ended.Ordered/deduplicated event channel or envelope.
Client intentDrive, aim, fire edge, ammunition, ready, team, rematch.Validated, ordered input with acknowledgement.

Viewer filtering occurs before serialization. A hidden enemy transform is omitted from that viewer's snapshot; the renderer is never asked to conceal secret coordinates it already received.

07 // Presentation

Three.js presents authority without inheriting it.

The browser bridge samples authoritative state into presentation entities. The render loop owns final visual synchronization so tanks are not fully synchronized twice in one frame. Remote poses interpolate across a bounded snapshot buffer; the local pose predicts the shared movement integrator and reconciles against authority.

✓
Critical state applies immediately.

Hit points, death, match transitions, and other durable facts are never delayed behind cosmetic work.

✓
Heavy effects are budgeted.

Smoke, debris, sparks, and remote destruction work can be admitted across frames without changing outcomes.

✓
Quality remains cosmetic.

Render scale, shadows, vegetation density, and effect budgets adapt. Combat rate, map dimensions, and armor resolution do not.

✓
Failure paths restore render state.

Off-screen targets and optional diagnostic resources are restored or disposed in guarded paths so later frames return to the visible target.

08 // Performance

Phase-aware loading and bounded frame work.

Performance policy begins with ownership. The garage does not activate a battlefield. Presentation routes do not preload the playable game graph. Optional networking, high-cost vehicle sources, and production tools remain dynamically reachable. Established hot loops reuse scratch state and avoid new per-frame allocations.

BudgetMechanismFailure behavior
BootStaged startup, module prewarm in development, garage-first world dormancy.Optional paths stay outside the critical graph.
CPU frameFixed-step cap, event admission budgets, reduced distant detail cadence.Cosmetics degrade before authority.
GPU frameAdaptive render scale, shadow policy, density and post tiers, shader warmup.Device rescue can disable optional passes.
NetworkSnapshot coalescing, deltas, baselines, keyframes, bounded extrapolation.Missing baselines wait for a keyframe.
MemoryResource reuse, explicit visual disposal, cached immutable worlds.Match-specific state resets independently.

09 // Studios and gallery

The shipped renderer is also the inspection environment.

/galleryreference + markup

The Tank Gallery loads one first-party procedural vehicle at a time. It combines searchable dossiers, armor/module/crew diagnostics, exact triangle or coplanar-patch selection, articulation ownership, and portable JSON/PNG review packets.

  • Audience: players, vehicle authors, and technical reviewers
  • Authority: canonical vehicle specifications and live procedural geometry
  • Shareable ?id=…&layer=… URLs
/studioproduction staging

Scene Studio composes live maps, tank actors, damage states, deterministic effects, camera rigs, and high-resolution captures without running combat AI.

  • Audience: artists, QA, marketing, automation
  • Round-trippable scene JSON
  • Frozen deterministic FX timeline
tools/verification

Browser probes, fleet geometry gates, screenshot contracts, icon generation, multiplayer soak rigs, performance recorders, and release checks turn visual or operational claims into reproducible artifacts.

  • Deterministic inputs and outputs
  • Focused checks before aggregate suites
  • Public/private artifact validation

11 // Verification

Proof is layered by failure surface.

The project does not use one test type as a universal proxy. Pure simulation and protocol invariants run in Node. Browser interaction and rendering use Chromium probes. Fleet assets bind to live metadata and geometry fingerprints. Public and private Vite builds verify route and quarantine behavior.

shell // release-oriented verification
# Complete deterministic self-test suite
npm test

# Browser multiplayer behavior
npm run test:net:browser

# Vehicle provenance and generated asset contracts
npm run tank:native:check
npm run tank:assets:check

# Deployable public and private artifacts
npm run build
npm run build:private
