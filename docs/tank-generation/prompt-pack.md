# Reusable tank-generation prompts

These are reconstructed briefs from the conversation's repeated requests and
the current repository contracts, not verbatim historical assistant prompts.
Replace angle-bracket fields, attach the actual sources, and keep one current
[run packet](templates/run-packet.md). A prompt never replaces reading the
applicable [procedure](SKILL.md) or grants publication on its own.

## 1. New source-backed X model

> Build `<display name> X` as exact ID `<id>` from `<source files>`. Read
> `docs/tank-generation/README.md` and follow its procedure. Preserve the current
> production model and unrelated fleet. Inspect/hash the actual supplied source,
> record provenance, freeze a source-only coordinate frame, and measure its
> hull, turret, gun, running gear and negative spaces before authoring.
> Create first-party procedural geometry, not a runtime source-file loader or
> an unrequested donor silhouette. Use the 92-point exemplar gates, independent
> 14-view review, correct physical attachments, both LODs and complete anatomy/
> release integration. Show the actual Gallery result and retain honest failures.
> Do not commit or push unless separately requested.

## 2. Full batch / family

> Build the explicit list `<IDs and sources>` as new X entries, preserving all
> existing models. First create a source/variant matrix and validate a
> representative small sample before scaling the batch. Assign disjoint profile
> owners and one shared-registry integrator. Identify which models are truly
> independent and which are explicitly authorized derivatives of `<base>`.
> Reuse validated first-party mechanics/recipes through bounded deltas, not a
> generic complete tank under each new name. For every variant, document unique
> hull/turret/kit differences and missing independent references. One base
> source does not certify the entire family. Finish each ID's measured/visual/
> combat/asset evidence and report a per-ID status table with the weakest gate.

## 3. Preserve Proto, replace the main model

> Keep the current `<id>` design as `<prototype name>` at `<tier>`, using a
> separately selectable `<prototype id>`. Pin its original first-party geometry
> before changes. Build a new proper `<id>` from `<source>` with the actual
> primary form and `<important recess/cutout>`. Do not overwrite the historical
> model or call a preservation comparison real-vehicle fidelity. Use the
> repository's audited preservation route only where supported; otherwise
> document and implement a tested preservation baseline before claiming it.

## 4. Explicit derivative

> Make `<target X>` based on our first-party `<base X>` recipe, while matching
> `<target source/configuration>`. Preserve the base's geometry and all original
> production variants. Reuse its construction functions with measured target
> datums; do not stack a second whole tank over it. Keep the target's distinct
> armor, sights, mantlet, gun, equipment and negative space. Reseat everything
> after reshaping and invalidate old target receipts until fresh verification.

## 5. Exact surface selection repair

> For `<id>`, use the attached Gallery markup to identify `<component>`.
> The requested action is `<attach/move/resize/remove/rebuild>`; the export's
> generic `operation: remove` is only selection metadata if it conflicts with
> this prose. Map local bounds, normals and selected owner at the recorded yaw/
> pitch, not unstable UUIDs/triangle indices alone. Change the smallest complete
> assembly needed, including its support, lenses, armor faces and dependent
> equipment. Preserve intentional openings. Verify the selected camera and
> opposing/low/top views plus non-neutral articulation; add a regression.

## 6. Real negative space / contact pass

> Rebuild `<recess/shoulder/chevron/bustle>` with actual measured surfaces.
> Preserve the real `<window/basket/ring/track>` air, but close accidental gaps
> inside the hull or turret. Give sight pockets side/rear/floor reveals instead
> of black painted rectangles. Join hull/glacis/shoulders/skirts with their own
> shaped solids. Keep permanent backing beneath removable ERA, and inspect
> intact, fully spent and reset states. Prove recess depth, contact and collision
> with paired images, sections/rays and the strict tool result, not a hole-count
> excuse or hidden filler.

## 7. Running-gear correction

> Fix `<id>`'s rear/front track wrap around the actual end-wheel centers.
> Preserve `<road-wheel centers/radii/other fixed datums>`; change only the
> requested `<end wheels/hull/track path>` and reseat all dependent parts.
> Keep one canonical suspension-owned wheel/track assembly. Recompute the
> tangent path and full visible shoe envelope, not just the hidden belt.
> Check both LODs, moving tracks, front/rear/side views and strict zero clip.
> Do not delete protected fenders/skirts or add a duplicate static track course
> to satisfy a silhouette or duplicate audit.

## 8. Shared machine-gun/attachment audit

> Audit the affected fleet `<IDs or reproducible shared handler>` for barrels
> rotated separately from receivers and floating fittings. Fix the actual shared
> cause if it is shared. Use a coherent assembly frame for barrel, receiver,
> cradle and support; default straight in the requested stowed pose, with no
> arbitrary per-barrel angle. Preserve legitimate source-specific folded or
> articulated configurations unless explicitly changed. Check real physical
> contact, national/configuration-specific weapon form and turret ownership.
> Hash-test unaffected models and exercise both high/low construction paths.

## 9. Independent critic brief

> Review `<candidate revision/fingerprint>` against `<source hash/frame>`.
> You own criticism only, not geometry or oracle edits. Inspect every required
> registered view plus the actual procedural Gallery path. Record per-view
> scores, weakest view, proportions, contours/rakes, real negative space,
> both-side winding, physical seats, yaw/pitch behavior, tracks and spent ERA.
> Target is ≥9/10 every required view and raw92 valid silhouettes/components,
> but do not award the target score by instruction. Mark missing evidence
> NOT RUN. Give exact locations/measurements, tests that would falsify each
> suspected defect, and a prioritized work order. One failed view blocks
> qualification; a detail count or attractive camouflage is not a substitute.

## 10. Resume / handoff

> Continue from `<handoff path>`. First verify its worktree, HEAD/dirty state,
> source hashes and last completed receipts against the live files. List any
> stale evidence. Resume the next exact bounded action, preserving other
> agents' work and the owner's latest target choices. Do not restart finished
> tanks or treat historical successes as current certification. Keep progress
> updates and a durable next-action checkpoint; report blocked/unrun checks
> distinctly from failures and publication status.

## 11. Commit and push

> Publish only `<explicit IDs/batch/path scope>` in `<one commit if requested>`
> to `origin/main`. Read the commit-and-push skill; inspect all diffs and current
> upstream changes. Exclude source models, quarantine exports, temporary QA and
> unrelated fleet/icon changes. Preserve complete required generated technical
> receipts. Rebase in an isolated integration worktree, resolve conflicts
> semantically, run fresh required checks, push without force and verify the
> remote hash. If qualification is incomplete, report exact failures and get
> explicit scoped as-is approval before publishing; previous batch approvals
> do not carry over. Never relabel failed gates as passed.

## 12. Target-choice questions (ask only when actually needed)

- “These two files depict the same tank but different source revisions. Do you
  want one X using both, or two separately named source studies?”
- “The supplied model's proportions conflict with published dimensions. Should
  this X match the file, or the real-vehicle dimensions? I'll retain both measurements.”
- “The supplied source lacks a roof weapon / contains real openings, while the
  current standard requires a weapon / continuity zero. Which configuration
  should I build? The raw conflicting gate will remain visible.”
- “This is a different pending batch from the one previously approved. It has
  these unresolved checks: `<list>`. Do you approve publishing this exact batch
  as-is, excluding `<sources/temp/unrelated work>`?”

Do not repeatedly ask choices already settled in the current run packet. Avoid
unnecessary clarifications for reversible details within the requested scope;
state measured assumptions and continue. User-specific size percentages or
forward shifts are local edits, not defaults for every future tank.
